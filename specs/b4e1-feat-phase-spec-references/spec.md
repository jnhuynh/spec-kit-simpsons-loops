# Feature Specification: Reference-Based Phase Child Specs

**Feature Branch**: `b4e1-feat-phase-spec-references`
**Created**: 2026-08-21
**Status**: Implemented
**Supersedes**: parts of `c31c-feat-phase-aware-specs` (Child Spec and Conflict Marker entities)

## Problem

Phase child specs generated by `/speckit-split` were populated copies of the parent: the parent's user stories, functional requirements, key entities, and success criteria were duplicated into each child, filtered to that phase's scope.

Duplication cost three things:

1. **Review burden.** A reviewer of a phase PR could not trust the child spec on its face. They had to diff it against the parent to confirm the child had not quietly altered a requirement — an expensive check that had to be repeated on every phase.
2. **Sync burden.** Two copies of the same requirement drift. The splitting skill carried a five-step reconciliation algorithm (baseline regeneration, section-by-section manual-edit detection, propagation from earlier phases, `<!-- CONFLICT: ... -->` markers, conflict reporting) whose entire purpose was to manage that drift.
3. **Ambiguity of authority.** With the same requirement in two files, nothing said which one won.

## Solution

A child spec is a **phase view** of the parent, not a copy of it. The parent holds every inherited item exactly once. The child names the items in its phase by ID and adds only what phasing itself requires.

### Two ID namespaces

| Namespace | Owner | Examples | Rule |
|-----------|-------|----------|------|
| Inherited | Parent spec | `User Story 3`, `FR-004`, `SC-002`, `Payment` | Listed by the child, never restated or redefined |
| Phase-local | Child spec | `FR-P2-001`, `SC-P2-001` | Requirements that exist only because the work is phased — feature flags, dark-launch scaffolding, backfills, compatibility shims |

The `P{N}` infix makes collision with parent IDs impossible, so a reader always knows which file authored a requirement.

### Child spec shape

```markdown
# Feature Specification: {feature name} - Phase {N}: {slug}

**Parent Spec**: `../{parent}/spec.md` <- AUTHORITATIVE
**Phase**: {N} of {total}    **Release Strategy**: {strategy}

> **This is a phase view, not a standalone spec.** ... Any agent or reviewer
> reading this file MUST read the parent sections named under Inherited Scope
> before planning, implementing, analyzing, or reviewing this phase.

## Inherited Scope        <- derived, regenerated on every split run
## Phase Boundary         <- authored, never overwritten
## User Scenarios & Testing / ## Requirements / ## Success Criteria
                          <- canonical headings kept for upstream Spec Kit
                             commands; each carries an `Inherited:` pointer
                             line plus any phase-local additions
```

Two kinds of content, and only one is derived. Split regenerates the metadata block, `## Inherited Scope`, and the `Inherited:` lines on every run; it never touches `## Phase Boundary` or the phase-local entries.

### Consumer resolution

Upstream `/speckit-plan`, `/speckit-tasks`, and `/speckit-analyze` belong to Spec Kit, not to this repo, and read only `FEATURE_DIR/spec.md`. Resolution is therefore belt-and-braces:

1. **In-file directive.** Every child spec opens with a mandatory block instructing any reader to resolve the parent before acting. This covers standalone command runs.
2. **Pipeline injection.** The `plan`, `tasks`, `lisa`, `ralph`, `marge`, and `pr-review` step playbooks detect the `--p{N}-` pattern and pass a parent-resolution paragraph to their sub agent. This covers the pipeline path, which is the primary one.

No generated `spec.resolved.md`, no markdown-slicing resolver script. Nothing to keep in sync, nothing extra to gitignore.

## What this deletes

- Split step 6e's baseline regeneration, section-by-section manual-edit detection, and earlier-phase propagation
- `<!-- CONFLICT: ... -->` markers and the Conflict Marker entity
- The conflict-reporting path in split's results output
- Recursive phasing (`phase` writing a `## Phases` section into a child spec)

## What this changes

| Component | Change |
|-----------|--------|
| `speckit-skills/speckit-split/SKILL.md` | Steps 6c-6e rewritten: pointer-only generation, derived-vs-authored refresh, no diffing. Manifest notice states the parent is the single source of truth |
| `speckit-skills/speckit-reconcile/SKILL.md` | **New.** Compares what Complete phases shipped against the parent and corrects the parent. Mechanical drift auto-fixed; intent-level drift reported `NEEDS_HUMAN` and left alone |
| `reference/steps/reconcile.md` | Targets `/speckit-reconcile <PARENT_DIR>` instead of re-running split on the parent |
| `reference/steps/{homer,premortem,phase}.md` | Child-spec skip clauses |
| `reference/steps/{plan,tasks,lisa,ralph,marge,pr-review}.md` | Parent-resolution instructions for child specs |
| `speckit-skills/speckit-pipeline/SKILL.md` | Child-spec step applicability (Step 3d), auto-detect routing, execution-plan announcement, `skipped` status definition |
| `README.md`, `CLAUDE.md` | Document the reference model |

## Why homer, premortem, and phase skip child specs

A child spec owns no user stories and no requirements of its own — there is nothing in it to clarify. Its risk register lives with the parent, dispositioned once for the whole feature before split ran. And it is already one phase of an already-phased parent; re-phasing it would nest deployment boundaries inside a boundary. A child-spec pipeline run is `reconcile -> plan -> tasks -> lisa -> ralph -> marge`.

## Success Criteria

- **SC-001**: A phase PR's child-spec diff contains only `## Phase Boundary` and phase-local `FR-P{N}-###` / `SC-P{N}-###` entries. No parent requirement prose appears in any child spec.
- **SC-002**: Editing a requirement in the parent requires no edit to any child spec, and is visible to every phase that references it.
- **SC-003**: Re-running `/speckit-split` on an unchanged parent leaves every child byte-identical, including authored content.
- **SC-004**: `homer`, `premortem`, and `phase` never execute against a directory matching `--p{N}-`.
- **SC-005**: The contract test at `tests/test-phase-spec-references.sh` passes.

## Migration

Child specs generated under the old model remain valid standalone specs and are not rewritten. The new shape applies to child specs generated or refreshed after this change. Converting an existing child is a manual edit: replace its copied sections with an `## Inherited Scope` table and renumber any phasing-only requirements into the `FR-P{N}-###` namespace.
